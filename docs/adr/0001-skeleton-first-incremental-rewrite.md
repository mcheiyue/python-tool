# 骨架先行 + 增量迁移的重写策略

项目要从既有分阶段演进的架构走向全新骨架，但应用当前可运行、部分测试可用。我们决定：先立最小目标骨架（目录结构 + 分层守护测试），用「批量重命名」作为垂直样例验证骨架契约，绿后按模块滚雪球迁移，旧架构代码在对应模块迁入后删除，最终全部退场；完成定义为「特征测试绿 + 应用可启动 + 原子提交」，骨架期走短分支。

**Status**: accepted

## Considered Options

- **大爆炸重写**（先完整新骨架再逐个移植）：拒绝——会丢弃已验证的可用状态，中间期无法运行验收。
- **仅架构层清理不迁功能**：拒绝——治不了 features 层的复制粘贴与线程债务（审查报告 P1 第 4/5/6 条），只换了个目录名。
- **全程 main 直接改**：拒绝——骨架半成品会破坏「每个提交可启动」的承诺。

## Consequences

- 每个迁移模块必须先有特征测试（或明确豁免），否则增量迁移无正确性判据。
- 模块迁移顺序按可验证性排序：纯逻辑 → 密封夹具 → 需真引擎（见 `docs/refactor_master_plan.md` §3）。
