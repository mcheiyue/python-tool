# Nuitka 编译缓存指南

## 什么是编译缓存？

Nuitka 在编译 Python 代码时会生成大量的 C 代码和中间编译产物，这些内容会存储在 `main.build/` 目录中。保留这些缓存可以**显著加速后续编译**。

---

## 缓存机制

### 缓存位置
```
dist/
├── standalone/
│   ├── main.build/          ← 编译缓存（500MB-1GB）
│   └── main.dist/           ← 最终产物（150MB）
└── onefile/
    ├── main.build/          ← 编译缓存（500MB-1GB）
    └── OfficeToolkit_Single.exe  ← 最终产物（80MB）
```

### 工作原理

**首次编译**（无缓存）：
1. Nuitka 分析所有 Python 代码
2. 生成对应的 C 代码
3. 使用 MinGW64 编译 C 代码
4. 链接所有依赖库
5. 打包资源文件
⏱️ **耗时：15-30 分钟**

**增量编译**（有缓存）：
1. Nuitka 检测哪些文件发生了变化
2. 只重新生成变化部分的 C 代码
3. 只重新编译变化的 C 文件
4. 重新链接（很快）
5. 更新资源文件
⏱️ **耗时：5-10 分钟**

## 优化后的脚本行为

### `build_nuitka.bat`（已优化）
✅ **保留缓存**：只删除 `main.dist/` 和最终的 `.exe` 文件  
✅ **智能提示**：检测到缓存时会显示提示


## 缓存管理

### 何时保留缓存？
✅ 日常开发和调试  
✅ 小幅修改代码后重新编译  
✅ 只修改了 UI 或业务逻辑  
✅ 依赖库没有变化

### 何时清理缓存？
⚠️ 更新了 Python 版本  
⚠️ 更新了主要依赖库（如 PyQt6、Nuitka）  
⚠️ 编译出现奇怪的错误  
⚠️ 需要确保完全干净的构建  
⚠️ 磁盘空间不足

## 手动清理缓存

### 方法一：使用清理脚本（推荐）
```batch
cd build
clean_cache.bat
```

这个脚本会：
- 列出将要删除的内容
- 询问确认
- 可选择是否清理全局缓存

### 方法二：手动删除
```batch
rmdir /s /q dist\standalone\main.build
rmdir /s /q dist\onefile\main.build
```

### 方法三：清理全局缓存
Nuitka 还会在用户目录维护一个全局缓存：
```
%LOCALAPPDATA%\Nuitka\Nuitka\Cache
```

清理命令：
```batch
rmdir /s /q "%LOCALAPPDATA%\Nuitka\Nuitka\Cache"
```

| 场景 | 缓存状态 | 编译时间 | 磁盘占用 |
|------|----------|----------|----------|
| 首次完整编译 | 无 | ~30 分钟 | ~150MB |
| 修改少量代码 | 有 | ~5-10 分钟 | ~1.5GB |

## Git 版本控制

缓存目录已添加到 `.gitignore`，**不会提交到仓库**：
```gitignore
# Nuitka 编译缓存（保留以加速增量编译）
dist/standalone/main.build/
dist/onefile/main.build/
```

这意味着：
- ✅ 本地可以享受缓存加速
- ✅ 不会污染 Git 历史
- ✅ 不会增加仓库体积
- ✅ 克隆仓库后首次编译会重新生成缓存

## 常见问题

### Q: 缓存会占用多少磁盘空间？
A: 
- 目录版缓存：~500-800MB
- 单文件版缓存：~500-800MB
- 总计约：~1-1.5GB

### Q: 缓存是否安全？可以随时删除吗？
A: 
- ✅ 完全安全，可以随时删除
- 删除后只是下次编译时间变长，不会影响功能

### Q: 为什么有时增量编译还是很慢？
A: 可能的原因：
- 修改了核心模块，触发大量重新编译
- 更新了依赖库
- Nuitka 检测到结构性变化

### Q: 如何判断是否在使用缓存？
A: 查看编译输出，如果看到：
```
[INFO] 检测到编译缓存，将加速构建过程
```
说明正在使用缓存。

### Q: CI/CD 环境需要缓存吗？
A: 
- 如果 CI/CD 每次都是干净环境：缓存无用
- 如果使用持久化构建节点：可以利用缓存加速

## 最佳实践

1. **开发阶段**：保留缓存，享受快速编译
2. **发布前**：清理缓存，确保干净构建
3. **定期清理**：每月清理一次，避免缓存膨胀
4. **依赖更新后**：清理缓存，避免兼容性问题
